  **Found and fixed a real bug**: `consumePasswordResetToken` originally ran the token-consume + password-update as a bare `db.transaction()`. `schema.ts`'s `users_update_self_only` policy requires `app.user_id` to equal the row being updated — a plain transaction never sets that (there's no session in this flow), so the `UPDATE users SET password_hash = ...` silently matched **zero rows** under RLS. No error, no exception — the token still got marked used, the action still returned success and redirected to `/login`, and only a direct DB check (`bcrypt.compare` against the stored hash) revealed the password had never actually changed. Only caught because dev is now genuinely RLS-enforced (ADR-0011) — this would have silently no-op'd in the pre-#8 setup where `neondb_owner` bypassed RLS entirely. Fixed by wrapping the update in `withUserContext(row.userId, ...)` once the token's own lookup (which *is* allowed session-less, via `password_reset_tokens`'s permissive select policy) has already cryptographically proven the caller holds a valid, unexpired, unused token for that specific user — treated as equivalent proof of identity to a session JWT, which is exactly what lets `withUserContext` satisfy `users_update_self_only` here.

  Verified live against Neon end to end (token generation via a throwaway script, since the actual emailed link can't be captured without a working `RESEND_API_KEY` — see below): valid token renders the real form; garbage/missing token renders the invalid-link state with no submittable form at all (confirmed a *reused* token correctly shows the same state, not just documented as intended); weak password, mismatched confirmation, and a non-existent email all handled correctly (the last one succeeding with the generic message, no email attempted); a full reset with a valid token updates `password_hash` for real this time (confirmed via `bcrypt.compare`, not just "the action returned success") and a subsequent login with the new password succeeds. **Not verified**: actually sending an email through Resend — `RESEND_API_KEY` isn't set yet (confirmed the code fails loudly with a clear error when it's missing, at least). Add the key (Vercel dashboard, Config type — not Secret, same reasoning as `DATABASE_URL` in #17) to finish this off; nothing else about the flow should need to change.
